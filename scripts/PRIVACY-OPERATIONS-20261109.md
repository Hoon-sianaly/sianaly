## 1. 사이트 운영자 기록

- `operator_access_audit`: 운영자 ID·시각·접속 IP·고정 업무명·자료 ID·조회/시도 구분·이벤트 ID·HMAC. 제보/글 본문·이메일·쿠키·비밀번호·인증 링크 제외.
- 본인이 일반 회원으로 이용하는 모든 활동을 일괄 기록하는 기능이 아님. 관리자 권한은 서버가 검증한 `app_metadata`만 사용.
- 관리 조회는 실제 반환할 자료 ID를 기록한 뒤 응답. 관리 변경은 시도 기록이 성공한 뒤 실행. 변경 시도 기록 자체가 변경 성공을 의미하지 않음.
- 감사 저장 실패 시 비공개 제보 반환·관리 변경을 차단. 이 상황의 503과 미변경을 회귀 테스트로 검증.
- 보관 366일. SQLite 트리거가 기록 수정과 조기 삭제를 거부하고 기간이 지난 행만 다음 처리에서 정리. 서버/원격 관리자 전체 권한까지 무력화하는 완전한 WORM이라고 주장하지 않음.
- 서명 검증용 파생키만 복구 공개키로 암호화해 `operator_audit_keys`에 보관. Supabase 서버 비밀키 원본을 저장/공개하지 않음. 비밀키가 교체돼도 기존 암호화 검증키로 과거 서명 검증 가능.
- 실제 D1 백업에서 접근기록 1건 서명과 복구 요청 1건 암호화 봉투 검증 성공. 백업 암호·개인키는 stdin/DPAPI로만 취급.

### 공급업체 콘솔 기록과 구분

Cloudflare 공식 자료상 계정 감사 로그는 모든 플랜에서 항상 활성, 18개월 보관. D1 문서에 열거된 것은 DB 생성/삭제/Time Travel 등 설정 작업이며 모든 SQL SELECT가 기록된다는 뜻이 아님.

Supabase 공식 문서상 조직 Platform Audit Logs는 Team/Enterprise 대상이며 Free 표준 API/DB 로그 1일과 다름. 본인 Account Audit 화면은 접근할 수 있었으나 이번에는 `You do not have any audit logs available yet` 표시. 이 화면 접근만으로 SQL·회원 조회의 1년 보관이 확인됐다고 하지 않음. 요금제 변경, 새 관리용 토큰, 외부 로그 전송 서비스는 임의 신청하지 않았음.

통상 운영은 사이트 관리 화면을 이용하고, 콘솔에서 회원 데이터를 직접 처리할 필요가 생기면 접근기록의 수집·장기 보관 경로를 별도로 확인해야 한다. 현 사이트 감사 기능을 공급업체 콘솔 전체를 감사하는 기능으로 안내하지 않는다. 해당 범위는 공개 전 별도 확인 과제다.

## 3. 복구 기록과 실제 재적용

### 자동 기록 범위

- 탈퇴 요청/탈퇴 성공, 글 삭제·수정, 즐겨찾기 삭제, 별명 변경.
- 글 수정·삭제는 D1 자료 변경과 복구 기록을 하나의 batch로 처리. 실제 D1 batch는 트랜잭션이며 실패 시 함께 롤백.
- 외부 Auth와 D1 간 탈퇴는 원자적 트랜잭션이 아니므로 요청과 성공을 구분. 요청만 남고 성공이 확인되지 않으면 복원 도구가 공개 허용을 거부한다.
- 별명/즐겨찾기는 본인이 요청한 삭제·정정 의도를 미리 기록. 원래 요청에서 외부 인증 서비스 오류가 있었던 경우도 복원 시 요청한 개인정보 보호 처리를 대조해야 한다.
- 암호화에는 서버 공개키만 사용. 복호화 개인키는 이 컴퓨터의 Windows DPAPI와 별도 백업 암호로 보호한 휴대 가능한 암호화 파일에만 저장. 개인키·백업 암호는 코드/GitHub/Cloudflare에 올리지 않음.
- 기록은 45일, 원 백업은 최대 30일 기준. 기간이 지난 기록은 다음 관련 처리에서 정리. USB 사본도 보관 기준 적용 필요.

### 실제 검증

1. 사용자가 지정한 본인 운영자 프로필의 네 항목 제거를 암호화한 재적용 기록 1건을 실제 D1에 저장. 원 회원 데이터를 다시 조회/삭제하지 않고 완료된 정리의 복원 방지 기록만 추가.
2. 이전 실제 PostgreSQL 백업 `sianaly-supabase-20261109T123518431Z.sianaly-backup`을 비공개 루프백 PostgreSQL에 복원.
3. 더 최근 D1 암호화 백업의 독립된 기록을 로컬 개인키로 해독해 재적용.
4. 본인 운영자 계정 존재 유지, `auth.users`와 같은 계정 `auth.identities`의 네 항목 잔존 0 확인. 다른 회원에 일괄 삭제하지 않음.
5. 별도로 실제 로컬 Auth·PostgREST·사이트 API를 사용하는 가입·메일 확인·로그인·글/댓글/추천·권한·재백업/복원·탈퇴 익명화·이전 세션 거부·로그아웃 7개 검사군 통과. 실제 회원 탈퇴나 외부 메일 발송 없음.
6. 최신 기록을 복원 DB에 다시 합치고 만료된 해결 제보·조회 구분값·시도 제한·인기 집계를 정리하는 보완도 실제 이전 백업 재적용 시험 통과. 최신 감사/삭제 기록이 후속 백업에서 사라지지 않도록 보존.
7. 생성된 평문 덤프·개인키·로컬 DB·시험 설정은 서버 종료 확인 후 임시 복원 폴더째 정리. 집계 증빙만 `tmp/backup-verification/`에 보존.

새 D1 백업(로컬): `sianaly-d1-20261109T144006638Z.sianaly-backup`. 서명 1건·암호화 요청 1건 검증, SQLite 무결성·외래키·내용 해시·독립 SQL 복원 통과. 파일은 공개 저장소/Pages 제외. 복구키 휴대용 파일 `sianaly-recovery-key.sianaly-backup`도 같은 제외·암호화 기준.

### 사고 복원 순서

1. 원본에 새 쓰기가 계속되는 상태에서 과거 백업으로 덮어쓰지 않는다. 서비스 접근을 차단하고 진행 중 요청을 정리한다.
2. **원본을 덮기 전에** 최신 독립 D1 백업을 읽기 전용으로 수집한다. 회원 DB 백업과 같은 오래된 시점의 기록만 사용하는 것은 금지.
3. 30일 이내 회원/게시판 백업을 `.secrets/backup/restore-UTC시각/`의 별도 PostgreSQL·SQLite로 복원한다.
4. `replay-private-recovery.ps1`에 최신 D1 암호화 백업, 복원 SQLite, 원 백업 UTC 시작 시각, 로컬 시험 DB 비밀번호를 SecureString으로 전달한다. 암호는 argv/채팅/공개 로그에 넣지 않는다.
5. 도구는 같은 비공개 폴더의 `127.0.0.1:55439 / restore_admin` DB만 허용. 오래된 독립 기록, 키/서명 불일치, 다른 경로, 미확인 탈퇴 요청이면 공개 허용을 내주지 않는다.
6. 삭제·정정 재적용, 최신 복구/감사 기록 병합, 만료 자료 정리 후 집계 증빙 확인. 수동 요청과 기록 도입 전 처리도 별도로 대조.
7. 실제 요청이 마지막 독립 사본 이후 유실되었다면 이를 자동으로 알아낸다고 보장할 수 없다. 원본 손실 범위와 마지막 기록 수집 시각을 확인하고 보완 검토를 마친 뒤 공개한다.

### 수동 개인정보 요청

이메일 등으로 받은 요청은 대상·권한을 최소 확인한 뒤 실제 조치 전에 `prepare-recovery-receipt.mjs`에 필요한 식별값과 정정값만 stdin JSON으로 전달한다. 허용되지 않은 부가 항목은 거부하며 DB는 직접 변경하지 않는다. 생성된 `.secrets/backup/receipt-UUID.sql`에는 암호화 봉투만 들어 있다. 운영자가 D1 콘솔에서 실행하고 건수만 확인한 후 실제 삭제·정정을 수행한다.

지원 종류: 탈퇴 요청/성공, 글 삭제/수정, 즐겨찾기 삭제, 별명 변경, 승인된 과거 프로필 네 항목 정리, 제보 삭제/개인정보 가림. 자료 삭제·가림에는 ID와 원 생성 시각을 함께 지정해 나중에 재사용된 다른 자료 ID에 잘못 적용하지 않는다. 탈퇴 성공 기록은 실제 완료 확인 후에만 생성한다. 요청 내용·신분증·비밀번호를 통째로 복구 기록에 넣지 않는다.

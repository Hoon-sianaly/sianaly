# SIANALY 전면 개편 계획안

작성: 2026-11-16 · 상태: **제안** (사장님 결정 전에는 아무것도 바꾸지 않음)

## 한 줄 요약

**화면에 보이는 내용(기업 설명, 실적 숫자, 디자인, 주소, 회원·게시글)은 그대로 두고**, 그 뒤에서 돌아가는 것들을 모두 새로 짭니다. 서버는 서울로 옮기고, 수천 개의 자료 파일은 데이터베이스 하나로 모으고, 페이지는 휴대폰이 아니라 서버가 완성해서 보내게 바꿉니다.

| 문서 | 개인정보처리방침·이용약관의 내용 (맡기는 업체가 바뀌는 부분만 고침) |

## 2. 지금 방식에서 문제가 되는 것

1. **서버가 멀어요.** 한국에서 들어와도 미국 로스앤젤레스 서버를 거쳐요. 한 번 다녀오는 데 0.3초 이상 걸리고, 처음 들어오는 사람은 화면 뼈대만 받는 데 0.9~2.9초가 걸려요. 휴대폰에서는 더 느려요.
2. **자료가 파일 수천 개로 흩어져 있어요.** 기업 자료가 JSON 파일 약 2,800개(54MB)예요. 기업 페이지 하나를 열 때 휴대폰이 파일 3~5개를 따로 받아서 직접 이어 붙여요.
3. **실적이 바뀔 때마다 사이트 전체를 다시 올려요.** 자동 업데이트가 하루 4번 코드 저장소에 자료를 저장하고, 그때마다 사이트 전체를 다시 배포해요. 11월에만 30번이에요. 배포가 실패하면 공시 반영도 같이 멈춰요.
4. **저장소가 두 군데예요.** 회원·즐겨찾기는 Supabase(서울)에, 게시판·인기 기업·제보·운영 기록은 Cloudflare 저장소에 있어요. 그래서 백업, 복구, 개인정보 안내를 모두 두 번씩 챙겨야 해요.
5. **화면을 휴대폰이 만들어요.** 페이지가 빈 껍데기로 도착하고 휴대폰이 자료를 받아 화면을 그려요. 검색 사이트를 위해 요약본을 따로 만들어 붙이는 장치도 필요해요.
6. **사람이 손으로 챙겨야 하는 게 많아요.**
   - 파일을 고칠 때마다 버전 표시(`?v=…`)를 직접 올려야 해요.
   - 개발 사이트와 실제 사이트의 저장 공간이 헷갈리기 쉬워요. 오늘 실제로 실수가 한 번 있었어요.
   - 처리방침 버전과 회원 동의 버전이 묶여 있어서, 문장 하나만 고쳐도 모든 회원이 다시 확인해야 해요.
7. **검색할 때마다 기업 목록 전체(약 97KB)를 받아요.** 첫 화면을 열 때마다 받아요.

## 3. 새 구조 (제안)

| 부분 | 지금 | 바꾼 뒤 |
|---|---|---|
| 서버 위치 | Cloudflare (한국 접속이 미국 LAX로 감) | **Vercel 서울** (유료 플랜) |
| 페이지 만드는 곳 | 휴대폰(브라우저)이 조립 | **서버가 완성해서 보냄** (Next.js). 많이 보는 기업 페이지는 미리 만들어 두고 바뀔 때만 새로 만듦 |
| 기업 자료 | JSON 파일 2,800여 개 | **데이터베이스 표** (Supabase 서울) |
| 게시판·인기 기업·제보·운영 기록 | Cloudflare D1 | **같은 데이터베이스**로 합침 |
| 회원·즐겨찾기 | Supabase | Supabase (그대로) |
| 실적 자동 업데이트 | 저장소에 저장 → 사이트 전체 재배포 | **데이터베이스에 바로 저장 → 바뀐 기업 페이지만 몇 초 안에 새로 고침** |
| 기업 검색 | 목록 전체를 받아 휴대폰에서 검색 | **서버에 물어보는 검색** (결과 몇 KB) |
| 개발/실제 사이트 | 저장 공간 두 개를 직접 구분 | 바꿀 때마다 **미리보기 주소가 자동으로** 생기고, 확인 후 "실제로 올리기"를 한 번 누르는 방식 |
| 파일 버전 표시 | 손으로 올림 | 자동 |
| 처리방침 버전 | 동의 버전과 묶임 | **문서 버전과 동의 버전을 분리**해서, 중요한 변경일 때만 다시 동의받음 |
| 보안 확인(Turnstile)·메일(Resend) | 사용 중 | 그대로 씀 |
| 도메인(sianaly.com) | Cloudflare에서 관리 | 관리는 그대로 두고 연결 대상만 Vercel로 바꿈 |

### 기대 효과 (목표치이고 보장은 아님)

- **휴대폰 첫 화면:** 몇 초 → 1초 안팎이 목표
- **기업 페이지:** 서버가 완성한 페이지가 바로 보여서, 숫자가 늦게 채워지는 일이 없어짐
- **공시 반영:** 자동 업데이트 후 사이트 반영이 수 분 → 수 초
- **운영:** 저장소가 하나가 되어 백업·복구·개인정보 안내가 단순해짐

## 5. 진행 순서

각 단계가 끝날 때마다 사장님이 확인하고 다음으로 넘어가요. **전환(7단계) 전까지 지금 사이트는 그대로 돌아갑니다.**

| 단계 | 내용 | 하는 사람 |
|---|---|---|
| 0. 준비 | Vercel 가입·결제, Supabase 플랜 결정, 이 계획 확정 | 사장님 |
| 1. 데이터베이스 | 표 설계. 지금 파일 자료를 그대로 옮겨 담고, **숫자 하나하나 원본과 100% 같은지 자동 대조** | 에이전트 |
| 2. 화면 | 지금 화면을 그대로 다시 만들기: 홈, 기업, 비교, 게시판, 자료 안내, 처리방침·약관, 마이페이지. 주소도 그대로 | 에이전트 |
| 3. 서버 기능 | 로그인, 즐겨찾기, 게시판, 제보, 인기 기업, 운영 기록을 옮기기. Cloudflare 저장소 자료도 옮기기. 지금 있는 검사들을 새 구조에서 다시 통과 | 에이전트 |
| 4. 자동 업데이트 | DART 실적 자동 업데이트가 데이터베이스에 쓰고, 바뀐 페이지만 새로 고치게 연결 | 에이전트 |
| 5. 미리보기 확인 | 새 미리보기 주소에서 PC·휴대폰으로 써 보고 속도 비교 | 사장님 |
| 6. 문서 고치기 | 처리방침의 맡기는 업체를 바꿔 쓰기 (Vercel 추가, Cloudflare 저장소 삭제 등). 회원에게 미리 안내 | 에이전트 작성, 사장님 확인 |
| 7. 전환 | 글쓰기를 몇 분 멈추고 마지막 자료를 옮긴 뒤 도메인 연결을 바꿈 | 사장님(연결 설정), 에이전트(자료) |
| 8. 정리 | 옛 사이트를 일주일 대기시킨 뒤 끄기, 새 백업 체계 만들기 | 에이전트 |

**예상 기간:** 제 작업 기준으로 2~4주예요. 사장님 확인 시간에 따라 달라져요.

## 7. 위험과 대비

| 걱정되는 점 | 대비 |
|---|---|
| 검색 순위가 떨어질까 | 주소를 그대로 쓰고, 사이트맵·대표 주소·제목·설명도 그대로 유지 |
| 회원이 로그인 못 할까 | 계정은 Supabase에 그대로 있어요. 전환 때 한 번 다시 로그인해야 할 수는 있어요 |
| 옮기는 중에 글·제보가 사라질까 | 전환 직전 몇 분만 글쓰기를 멈추고 마지막으로 옮긴 뒤, 개수와 내용을 대조 |
| 숫자가 틀리게 옮겨질까 | 1단계에서 원본 파일과 데이터베이스를 자동으로 전부 대조하고, 하나라도 다르면 진행하지 않음 |
| 새 사이트에 문제가 생기면 | 옛 사이트를 일주일 동안 그대로 두어서, 도메인 연결만 되돌리면 바로 복귀 |
| 처리방침 | 업체가 바뀌므로 전환 전에 새 버전으로 고치고 안내 |
| 비용이 늘까 | 각 서비스에 사용량 알림을 설정 |

## 8. 정해 주실 것

1. **옮길 곳:** Vercel(추천, 관리 쉬움)로 할지, AWS 서울 서버를 직접 관리할지(더 싸지만 관리 부담 큼)
2. **Supabase:** 무료로 시작할지, 처음부터 유료로 할지
3. **시작 시점**
4. **주가 표시:** 금융위원회 답변이 오면 이번 개편에 같이 넣을지
